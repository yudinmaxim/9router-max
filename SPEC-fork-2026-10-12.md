# Спецификация доработок форка 9router-max

Дата: 2026-10-12
Ветка: `max`
Форк: `git@github.com:yudinmaxim/9router-max.git` (origin), апстрим `git@github.com:decolua/9router.git` (upstream)

Каждая задача самодостаточна, содержит список конкретных правок, критерии приёмки и
команды проверки. Задачи выполняются строго по порядку. Каждая завершённая задача —
один коммит в стиле Conventional Commits.

## Глобальные правила

- Тесты: `cd tests && npx vitest run <файл>`. Корневой `npm test` не запускает тесты.
- После правок реестра или алиасов обязательно: `cd tests && npx vitest run __baseline__/verify-no-regression.mjs`
- До правок известно 64 красных теста; сверять изменения с `tests/__baseline__/known-fails.txt`.
- `open-sse/providers/registry/index.js` генерируется скриптом `scripts/migrate-registry.mjs`,
  руками не редактировать. Шаблон — `REGISTRY_TEMPLATE.js`.
- Новый транслятор обязан быть импортирован в `open-sse/translator/index.js`.
- Любой код, мутирующий запрос (`open-sse/rtk/`, headroom, MCP-инжектор), при ошибке
  обязан возвращать исходное значение или `null` — fail-open.
- Перед правкой в `open-sse/` читать `open-sse/AGENTS.md`.
- Правило стиля: без комментариев в коде.

## Порядок выполнения

# Задача 1. Ошибка провайдера должна доходить до клиента

## Проблема

При исчерпании лимита провайдер возвращает ошибку внутри успешного по HTTP ответа:
`200 OK` и SSE-поток, в котором один кадр `data: {"error": ...}`.

Этот кадр теряется по пути:

1. `open-sse/executors/opencode.js:416` — принудительно выставляется `stream: true`.
2. Ответ приходит с кодом 200, поэтому ветка `!providerResponse.ok` в
   `src/sse/handlers/chatCore.js:481` не срабатывает.
3. `open-sse/utils/stream.js:273` `parseSSELine` разбирает кадр, `:373` `translateResponse`
   передаёт его в конвертер ответа.
4. `open-sse/translator/response/openai-to-claude.js:72` содержит
   `if (!chunk || !chunk.choices?.[0]) return null` — кадр с ошибкой не имеет `choices`,
   поэтому конвертер возвращает `null`, и кадр отбрасывается.
5. `flush()` в `open-sse/utils/stream.js:494` тоже возвращает `[]`.
6. `message_stop` не синтезируется. В протоколе Anthropic завершение ответа — это
   именно `message_stop` (маркера `[DONE]` нет), поэтому клиент ждёт бесконечно.

Затрагивает любой клиент, использующий Anthropic-формат. OpenAI-совместимые клиенты
не зависают, потому что там есть `[DONE]`.

Подтверждение: в `~/.9router/db/data.sqlite` в таблице `usageHistory` нет ни одной
строки со статусом `FAILED`, таблица `requestDetails` пуста — ошибка не фиксируется
вообще.

Второй дефект: `src/sse/services/auth.js:246` содержит
`if (!connectionId || connectionId === "noauth") return { shouldFallback: false }`.
У провайдеров без авторизации (`opencode`) `connectionId` не задан
(`src/sse/services/auth.js:58` возвращает `id: "noauth"`), поэтому автоматическое
переключение на резервное соединение для них физически невозможно. Правило обработки
429 существует в `open-sse/services/accountFallback.js:23` (`checkFallbackError`),
но до этих провайдеров код не доходит.

## Правки

- [ ] 1.1 В `open-sse/translator/response/openai-to-claude.js` научить конвертер
      распознавать кадры с ошибкой и превращать их в корректный Anthropic-блок ошибки
      вместо `return null`.
- [ ] 1.2 В `open-sse/utils/streamHelpers.js:139-147` в функции `buildStreamErrorBytes`
      дописать формирование `message_stop` для Claude-ветки, чтобы поток всегда
      закрывался терминальным событием.
- [ ] 1.3 В `open-sse/utils/stream.js:494` убедиться, что `flush()` возвращает
      терминальное событие даже при отсутствии данных.
- [ ] 1.4 В `src/sse/services/auth.js:246` разрешить переключение для провайдеров
      с `connectionId === "noauth"`.
- [ ] 1.5 Добавить тест: поток с единственным кадром `data: {"error": {...}}`
      обязан породить ошибку и `message_stop`.

## Критерии приёмки

- [ ] Клиент с Anthropic-протоколом получает ошибку, а не зависает.
- [ ] В `usageHistory` появляется запись со статусом `FAILED`.
- [ ] Поток с ошибкой всегда закрывается `message_stop`.

# Задача 6. Прямое подключение в обход прокси

Задача снята по решению пользователя.

Причина, зафиксированная для истории: Karing работает в режиме TUN
(`tun.enable=true`, `auto_route=true`, `allow_bypass=false`,
`route_exclude_address=[]`, `perapp.list_macos=[]`), что доказано состоянием системы:
интерфейс `utun4` с адресом `10.20.0.1` и `mtu 4064` совпадает с настройками Karing,
а в таблице маршрутизации `default link#19 utun4` стоит выше по приоритету, чем
`default 192.168.1.1 en0`. Приложение не может исключить себя из сетевого расширения,
поэтому переключатель «соединяться напрямую» в роутере задачу не решает.

Дополнительно: собственный прокси в роутере сейчас не настроен — `launchctl getenv`
пусто, `outboundProxyEnabled:false`, таблица пулов прокси пуста.

# Задача 7. Выгрузка и загрузка конфигурации

## Что уже есть

Функция уже реализована: `GET/POST /api/settings/database`
(`src/app/api/settings/database/route.js`), функции `exportDb` и `importDb`
(`src/lib/db/index.js:73-96` и `:104-122`), интерфейс на странице профиля
(`src/app/(dashboard)/dashboard/profile/page.js:663-740`) — скачивание файла
`9router-backup-<timestamp>.json` и загрузка обратно. Экспортируется 7 таблиц из 11.

Задача не в том, чтобы строить с нуля, а в том, чтобы сделать существующее безопасным,
переносимым между машинами и с осознанным выбором.

## Решение по режимам

Два режима на выбор пользователя:

- **Конфиг** (по умолчанию) — подключения без токенов, настройки, алиасы,
  `customModels`, `disabledModels`, комбинации, MCP-серверы, пулы прокси без
  логина и пароля. Для обмена конфигурацией.
- **Полный перенос** — дополнительно `accessToken`, `refreshToken`, `idToken`, `apiKey`,
  ключи роутера `sk-...`, пути прокси с учётными данными. Для переноса на свою вторую
  машину. С явным предупреждением.

Важный факт: в базе токены лежат **открытым текстом**. Шифрования в покое нет
нигде, кроме одного поля `mitmSudoEncrypted`. Поэтому второй режим честно
называется файлом с секретами.

## Правки

## Проверка перед деплоем

- [ ] 10.1 Стенд на отдельных данных и порту 20129. Запускать нужно **собранный
      standalone** (тот же артефакт, что уезжает на живой), а не `npm start`: в
      репозитории скрипт `start` — это `node custom-server.js --port 20127`,
      он жёстко задаёт порт и переменная `PORT` не подхватывается, поэтому такой
      запуск либо поднимет стенд на 20127, либо вообще не поднимется как задумано.
      Порт standalone читает из окружения (`.next/standalone/server.js:8`,
      `parseInt(process.env.PORT) || 3000`), поэтому корректно:
      `cd .next/standalone && DATA_DIR=/tmp/9router-stage PORT=20129 node custom-server.js`
      `DATA_DIR` поддерживается, `src/lib/dataDir.js:18`.
- [ ] 10.2 Запускать стенд именно через `custom-server.js`, а не через голый
      `server.js`. `cli.js` (строка ~547) в живом инстансе отдаёт предпочтение
      `custom-server.js` — он ставит `NINEROUTER_PEER_TOKEN` и оборачивает
      `http.createServer` (реальный IP сокета, h2c). Голый `server.js` этого не
      делает, и стенд перестанет быть эквивалентом живому. Файл `custom-server.js`
      приезжает в `.next/standalone/` при сборке, так что он доступен без
      дополнительных шагов.
- [ ] 10.3 Прогнать на стенде полный список моделей, а не только `ca/*`.
      Сейчас `9router-fork-sync` проверяет только `ca/*`
      (строки 96-97), поэтому opencode и omp прошли бы вслепую.
- [ ] 10.4 Расширить проверки в `9router-fork-sync`: все схемы провайдеров,
      счётчик моделей, пробный запрос чата.
- [ ] 10.5 Перенести проверку до подмены `app/`, а не после неё.
- [ ] 10.6 Добавить флаг `--rollback` в `9router-fork-sync`.
      Предыдущая сборка уже хранится в `app.npm.bak` (строки 61-68), откат
      сводится к обратной подмене.
- [ ] 10.7 Починить `~/.local/bin/9router-fix`: он патчит устаревший путь
      `.next-cli-build/...` и старую схему, не определяет, какой из каталогов
      сборки используется, не проверяет, применён ли патч уже, и не имеет отката.
- [ ] 10.8 **Не делить OAuth-токены между стендом и живым.** Наполнять стенд
      копией боевой базы можно для проверки конфигурации, списка моделей и
      алиасов — это безопасно. Но гонять на стенде тесты, которые дёргают
      обновление токенов, нельзя: у провайдеров с ротацией `refreshToken`
      (kimi, grok, trae, xai) обновление на стенде делает записанный у живого
      `refreshToken` невалидным, и живой упадёт на следующем обновлении.
      Правильный порядок: переавторизовать провайдера на самом стенде, чтобы у
      него появились собственные токены. У cursor это неактуально — там
      `refreshToken` вообще `null`, публичного refresh-endpoint нет.
