# Спецификация доработок форка 9router-max

Дата: 2026-10-12
Ветка: `max`
Форк: `git@github.com:yudinmaxim/9router-max.git` (origin), апстрим `git@github.com:decolua/9router.git` (upstream)

Каждая задача самодостаточна, содержит список конкретных правок, критерии приёмки и
команды проверки. Задачи выполняются строго по порядку. Каждая завершённая задача —
один коммит в стиле Conventional Commits.

## Глобальные правила

- Тесты: `cd tests && npx vitest run <файл>`. Корневой `npm test` не запускает тесты.
- После правок реестра или алиасов обязательно: `cd tests && npx vitest run __baseline__/verify-no-regression.mjs`
- **Сверять изменения с `tests/__baseline__/known-fails.txt` нельзя** — он устарел:
  каталогизирует 24 падения, фактически их 101. Скрипт `verify-no-regression.mjs`
  вдобавок нерабочий: строит имена как `f.name.split("/app/")[1]`, а путь `/app/`
  в путях тестов не встречается, поэтому все записи начинаются с `undefined ::`.
  Надёжный способ: прогнать подозрительные файлы дважды — на чистом дереве
  (`git checkout -- <файлы>`) и с правками — и сравнить списки падений. Именно так
  подтверждено отсутствие регрессий в задаче 1.
- `open-sse/providers/registry/index.js` генерируется скриптом `scripts/migrate-registry.mjs`,
  руками не редактировать. Шаблон — `REGISTRY_TEMPLATE.js`.
- Новый транслятор обязан быть импортирован в `open-sse/translator/index.js`.
- Любой код, мутирующий запрос (`open-sse/rtk/`, headroom, MCP-инжектор), при ошибке
  обязан возвращать исходное значение или `null` — fail-open.
- Перед правкой в `open-sse/` читать `open-sse/AGENTS.md`.
- Правило стиля: без комментариев в коде.

# Задача 1. Ошибка провайдера должна доходить до клиента

## Проблема

При исчерпании лимита провайдер возвращает ошибку внутри успешного по HTTP ответа:
`200 OK` и SSE-поток, в котором один кадр `data: {"error": ...}`, после чего поток
закрывается штатно.

Диагноз уточнён чтением кода — исходная формулировка в спеке была неверна:

- Существующий `buildStreamErrorBytes` (`open-sse/utils/streamHelpers.js`) **уже**
  отдаёт `event: error` для Claude. Дописывать `message_stop` не нужно.
- Настоящая причина зависания: `onAbortTerminal`, а с ним весь error-механизм,
  вызывается **только при аварии** — обрыве, stall-таймауте, дисконнекте
  (`pipeWithDisconnect`, `open-sse/utils/streamHandler.js:195`; `onAbortTerminal`
  на строке 93 `streamingHandler.js`). Провайдер в нашем случае отдаёт `200 OK`,
  затем кадр с ошибкой, и **закрывается штатно** → это обычный EOF, ошибка нигде не
  фиксируется, `flush()` пуст, клиент получает 200-поток без терминального события.
- `parseSSELine` отдаёт объект как есть, кадр с ошибкой доходит целым.
- `open-sse/translator/response/openai-to-claude.js:72` (`return null` при
  отсутствии `choices`) — реальная причина отбрасывания кадра, но править его
  отдельно не нужно: перехват поставлен **до** `translateResponse`, поэтому все
  конвертеры закрыты одной точкой.

Затрагивает любой клиент, использующий Anthropic-формат. OpenAI-совместимые клиенты
получают кадр с ошибкой, но без `[DONE]`, то есть ответ выглядит как пустое
завершение.

Подтверждение: в `~/.9router/db/data.sqlite` в таблице `usageHistory` нет ни одной
строки со статусом `FAILED`, таблица `requestDetails` пуста — ошибка не фиксируется
вообще.

Второй дефект: `src/sse/services/auth.js:246` содержал
`if (!connectionId || connectionId === "noauth") return { shouldFallback: false }`.
У провайдеров без авторизации (`opencode`) `connectionId` не задан
(`src/sse/services/auth.js:58` возвращает `id: "noauth"`), поэтому автоматическое
переключение на резервное соединение для них физически невозможно. Правило обработки
429 существует в `open-sse/services/accountFallback.js:23` (`checkFallbackError`),
но до этих провайдеров код не доходит.

## Правки

- [x] 1.1 `open-sse/utils/streamHelpers.js`: добавить `extractStreamError(chunk)`,
      `toHttpStatus()`, `STREAM_ERROR_TYPE_STATUS`, `resolveStreamErrorStatusFromHint()`;
      `buildStreamErrorBytes` разбить на `buildStreamErrorFrame` (возвращает строку)
      и обёртку в байты. Импорты: `HTTP_STATUS` из `../config/runtimeConfig.js`,
      `DEFAULT_ERROR_MESSAGES` из `../config/errorConfig.js`.
- [x] 1.2 `open-sse/utils/stream.js`: флаг `streamErrorStatus` и хелпер
      `emitStreamError(controller, chunk)` (ставит статус, пишет кадр, логирует,
      зовёт `finalizeStream()`). Вызовы в 4 местах: passthrough-ветка, translate-ветка,
      хвостовой буфер в `flush()`, плюс guard в начале `transform`.
- [x] 1.3 `open-sse/utils/stream.js`: `finalizeStream` при ошибке пишет
      `FAILED ${streamErrorStatus}` вместо `200 OK`. Пункт про синтез `message_stop`
      снят — не требуется.
- [x] 1.4 `src/sse/services/auth.js`: константа `NOAUTH_CONNECTION_ID = "noauth"`.
      В `getProviderCredentials` условие `FREE_PROVIDERS[providerId]?.noAuth` дополнить
      `&& !excludeSet.has(NOAUTH_CONNECTION_ID)` — критично, иначе цикл в `chat.js:246`
      (`while(true)`) станет бесконечным, второй проход вернул бы те же синтетические
      креды. Именно поэтому защита изначально и существовала.
- [x] 1.5 `src/sse/services/auth.js`: `markAccountUnavailable` больше не отказывает по
      синтетическому id — добавлен флаг `isSynthetic`, запись в БД и `log.warn` о
      блокировке выполняются только для реальных подключений. `clearAccountError`
      использует константу.
- [x] 1.6 Тест `tests/unit/stream-error-frame.test.js`, 13 тестов.

## Критерии приёмки

- [x] Клиент с Anthropic-протоколом получает ошибку, а не зависает.
- [x] В `usageHistory` появляется запись со статусом `FAILED <код>`.
- [x] Поток с ошибкой закрывается терминальным событием (`event: error` для Claude,
      кадр + `[DONE]` для OpenAI).
- [x] Регрессий нет: чистое дерево и дерево с правками дают одинаковые 101 падение,
      все они зафиксированы как существовавшие ранее.

# Задача 6. Прямое подключение в обход прокси

Задача снята по решению пользователя.

Причина, зафиксированная для истории: Karing работает в режиме TUN
(`tun.enable=true`, `auto_route=true`, `allow_bypass=false`,
`route_exclude_address=[]`, `perapp.list_macos=[]`), что доказано состоянием системы:
интерфейс `utun4` с адресом `10.20.0.1` и `mtu 4064` совпадает с настройками Karing,

# Задача 7. Выгрузка и загрузка конфигурации

## Что уже есть

Функция уже реализована: `GET/POST /api/settings/database`
(`src/app/api/settings/database/route.js`), функции `exportDb` и `importDb`
(`src/lib/db/index.js:73-96` и `:104-122`), интерфейс на странице профиля
(`src/app/(dashboard)/dashboard/profile/page.js:663-740`) — скачивание файла
`9router-backup-<timestamp>.json` и загрузка обратно. Экспортируется 7 таблиц из 11.

Задача не в том, чтобы строить с нуля, а в том, чтобы сделать существующее безопасным,
переносимым между машинами и с осознанным выбором.

## Решение по режимам

Два режима на выбор пользователя:

- **Конфиг** (по умолчанию) — подключения без токенов, настройки, алиасы,
  `customModels`, `disabledModels`, комбинации, MCP-серверы, пулы прокси без
  логина и пароля. Для обмена конфигурацией.
- **Полный перенос** — дополнительно `accessToken`, `refreshToken`, `idToken`, `apiKey`,
  ключи роутера `sk-...`, пути прокси с учётными данными. Для переноса на свою вторую
  машину. С явным предупреждением.

Важный факт: в базе токены лежат **открытым текстом**. Шифрования в покое нет
нигде, кроме одного поля `mitmSudoEncrypted`. Поэтому второй режим честно
называется файлом с секретами.

## Правки

- [ ] 7.1 Основная проблема: `exportDb` отдаёт все секреты без исключений.
      `PROTECTED_SETTING_KEYS = ["password", "mitmSudoEncrypted"]`
      (`src/app/api/settings/route.js:15`) к экспорту не применяется, потому что
      `exportSettings()` (`src/lib/db/repos/settingsRepo.js:140-142`) читает сырое
      значение. Это одновременно и дыра, и причина сделать выбор режима обязательным.
- [ ] 7.2 Реализовать режим без секретов. Вырезать: `accessToken`, `refreshToken`,
      `idToken`, `apiKey`, `settings.password`, `settings.oidcClientSecret`,
      `settings.mitmSudoEncrypted`, `apiKeys.key`, учётные данные внутри `proxyUrl`,
      `providerOverrides.*.headers`.
- [ ] 7.3 `providerSpecificData` чистить по белому списку, а не по чёрному. Там
      лежат и не-секреты, нужные для работы: `cursor.machineId`, `kimi.deviceId`,
      `trae.tenant` и `webId`, `codex.chatgptAccountId`, `qoder.organizationId`. И
      одновременно секреты: `grok-cli.idToken`, `copilotToken`
      (`src/app/api/providers/client/route.js:14-21` — образец `SAFE_PSD_FIELDS`).
      Чёрный список по именам здесь не сработает.
- [ ] 7.4 `mitmSudoEncrypted` выбрасывать в обоих режимах: ключ выводится из
      `machineIdSync()` (`src/mitm/manager.js:154-162`), на другой машине значение

      введёт пароль sudo.
- [ ] 7.5 Добавить конверт файла: `formatVersion`, `exportedAt`, `sourceVersion`,
      `mode`, `payload`. Сейчас импорт не знает версию схемы и не отличает свой файл

- [ ] 7.6 Перед импортом делать бэкап. Сейчас `importDb` сначала стирает таблицы
      (`src/lib/db/index.js:104-112`), потом пишет, восстановления нет — неудачный
      импорт уничтожает конфиг целиком. Обернуть в существующий `backupDbLite`
      (`src/lib/db/backup.js`).
- [ ] 7.7 Добавить режим слияния. Сейчас только полная замена. Нужен вариант
      «наложить поверх» с дедупликацией по паре `proxyUrl + noProxy` — паттерн уже
      готов в `dashboard/proxy-pools/page.js:561-589`.
- [ ] 7.8 При импорте сбрасывать `expiresAt` и `lastRefreshAt`: `refreshToken`
      одноразовый, перенос устаревшего значения на машину, где его уже обновили,
      даст жёсткий отказ (комментарий в `connectionsRepo.js:164-168`).
- [ ] 7.9 Добавить `disabledModels` в экспорт и импорт — сейчас этот раздел `kv` не
      переносится (`src/lib/db/index.js:90-93`, `:112`), поведение асимметричное:

- [ ] 7.10 Ключи роутера `sk-...` по умолчанию не выгружать. Валидация у них —
      простая сверка строк (`apiKeysRepo.js:84-89`), то есть такой файл даёт полный

- [ ] 7.12 Поправить ложную подпись в интерфейсе:
      `src/app/(dashboard)/dashboard/providers/new/page.js:163` обещает «Your API key

- [ ] 7.13 Тесты: расширить `tests/unit/db-sqlite-vs-lowdb.test.js:344`

## Критерии приёмки

- [ ] Файл без секретов не содержит ни одного токена — проверяется тестом по всем полям.
- [ ] Импорт конфига без секретов поднимает рабочую конфигурацию, кроме авторизаций.

- [ ] Файл старого формата (без конверта) либо принимается, либо отвергается с понятным сообщением.

## Проверка перед деплоем

- [ ] 10.1 Стенд на отдельных данных и порту 20129. Запускать нужно **собранный

      делает, и стенд перестанет быть эквивалентом живому. Файл `custom-server.js`

# Задача 8. Починка тестовой инфраструктуры

## Почему задача вообще существует

Гейт регрессий `tests/__baseline__/verify-no-regression.mjs` никогда не работал.
Он строил имя теста как `f.name.split("/app/")[1]`, а подстрока `/app/` в путях,
которые отдаёт vitest, не встречается. Все записи начинались с `undefined ::`,
сравнение с `known-fails.txt` было бессмысленным — гейт зелёный всегда, независимо
от состояния кода.

Вдобавок результат прогона зависел от текущего каталога: часть тестов использовала
`path.resolve("src/...")` (ждёт cwd=корень репозитория), часть — `path.resolve("../src/...")`
(ждёт cwd=`tests/`). Ни один способ запуска не покрывал все файлы.

Следствие: «101 падение против 87» было не регрессией, а двумя разными прогонами,
считающими разные наборы файлов.

## Решение по baseline

Принцип: **baseline — это текущий HEAD, а не чистое дерево апстрима.**
Форк ушёл далеко от родительского репозитория намеренно, обратных мержей не
планируется. Эталон должен отражать текущее состояние, а не чужое.

Сгенерирован на текущем HEAD: 94 записи. Из старых 24 десять (`rtk.test.js`) уже
починены и выброшены.
